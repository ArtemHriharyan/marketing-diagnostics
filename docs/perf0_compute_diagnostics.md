## 2. Находка №1 — `compute_funnels` считается три раза

`compute_funnels(paths)` вызывается тремя независимыми потребителями, каждый
раз с нуля, без кэша:

- `src/compute/funnels.py:289` — `run()` пишет `funnels.json`;
- `src/compute/block3.py:819` — `_run_c06`;
- `src/compute/seasonality.py:151` — `_funnel_series`.

cProfile: `funnels.py:226(compute_funnels)` — `ncalls=3`, `cumtime=10.487 с`
из 16.055 с всего dispatch (под профайлером). Без профайлера — ~2.0 с на
вызов, то есть **≈6.1 с из 9.9 с dispatch, из них ≈4.1 с — чистый дубль**.

Косвенное подтверждение: собственная работа `seasonality` вне
`compute_funnels` — 2.364 − 2.111·(доля `_funnel_series` 3.542/3.599) ≈ 0.06 с;
`block3` вне `_run_c06` ≈ 1.2 с. Оба блока почти целиком состоят из ожидания
воронок.

## 3. Находка №2 — сегментный цикл `compute_funnels` квадратичен

`funnels.py:259-274`: для каждого разреза `_SEGMENT_COLUMNS`
(`month`, `channel`, `device`, `entry_page`) и **каждого его значения**
строится `segment_visits` полным проходом по всем визитам:

```python
segment_visits = {
    visit_id for visit_id in all_visit_ids if visits[visit_id].get(column) == value
}
```

Сложность — `O(число значений разреза × число визитов)` на чистом Python.
Отсюда 17 356 335 вызовов `dict.get` (3.63 с tottime) в профиле.

Замер стоимости на pognali.rent:

| Разрез | Значений | Сбор сегментов | Пар (значение × визит) | с/10⁶ пар |
|---|---:|---:|---:|---:|
| month | 15 | 0.227 с | 513 405 | 0.44 |
| channel | 5 | 0.087 с | 171 135 | 0.51 |
| device | 4 | 0.073 с | 136 908 | 0.53 |
| entry_page | 107 | 1.245 с | 3 662 289 | 0.34 |

`repeat_by_stage` (`funnels.py:248-257`) — тот же паттерн, но дешевле:
2 этапа × 34 227 визитов = 0.035 с.

## 4. Находка №3 (главная) — `220volt.kz` не досчитается

`clients/220volt.kz/data/canonical/`: **752 382 визита**, `visits.parquet`
51.9 МБ. `entry_page` — **28 689 различных значений**.
В `clients/220volt.kz/config.yaml` воронка `booking` **настроена**, то есть
ранний выход `compute_funnels` («funnels не настроены») не сработает.

Замер на реальных данных 220volt.kz (по 20 значениям каждого разреза,
линейная экстраполяция на все значения — цикл линеен по числу значений):

| Разрез | Значений | мс/значение | Весь разрез |
|---|---:|---:|---:|
| month | 12 | 631.5 | 7.6 с |
| channel | 4 | 758.3 | 3.0 с |
| device | 4 | 775.4 | 3.1 с |
| **entry_page** | **28 689** | **540.6** | **15 508 с = 4.31 ч** |

Плюс `_load_visit_data` — 3.49 с на вызов.

**Итог: ≈4.3 ч на один `compute_funnels`, ×3 вызова ≈ 12.9 ч на стадию
`compute` для 220volt.kz.** Практически — стадия не завершается.

Важно: высокая кардинальность `entry_page` здесь **настоящая**, а не грязь в
URL. Доля значений с query-string — 0.0%; после `split_part(entry_page,'?',1)`
и снятия хвостового `/` остаётся ровно те же 28 689 значений. Топ страниц:
`/` (66 319 визитов), `/search` (32 799), `/catalog` (10 341). Значит **URL-1
и CRAWL-1 эту проблему не закрывают** — это алгоритм, а не нормализация.

Побочный эффект того же места — размер артефакта: `funnels.json` для
pognali.rent = 163 549 б на 131 сегмент (~1.25 КБ/сегмент). При 28 689
сегментах это ≈36 МБ, и дальше — во вход `analyze`.

## 6. Блокеры, найденные попутно (вне периметра «производительность»)

### 6.1 Отсутствие зависимости роняет стадию целиком, а не деградирует

В окружении не было `scipy` (есть в `requirements.txt`). `block1.py:162`
импортирует `from scipy import stats` на уровне модуля, а
`common.dispatch_blocks` вызывает `_import_block` **вне** `try`
(`src/compute/common.py:294`) — `ModuleNotFoundError` уходит наружу и обрушивает
весь `compute`, хотя соседние блоки к scipy отношения не имеют. Это расходится
с принципом 4 и с собственным контрактом `dispatch_blocks` («любая ошибка блока
не должна ронять весь compute»).

Для замеров установлен `scipy 1.18.0`. Из `requirements.txt` в окружении
по-прежнему нет: `openai`, `playwright`, `tapi-yandex-metrika`
(на `compute` не влияют — влияют на `analyze`/`extract`).

### 6.2 `compute` недетерминирован между прогонами

Два подряд прогона `compute` на неизменных данных дают **23 различающихся
файла**: `a14`, `c04`, `c05`, `c12`, `d04`, `d08`, `s01`, `s02`, `s03`, `s25`
(`.csv` и `.json`) и `analysis_candidates.json`.

Это **не** хеш-рандомизация: с `PYTHONHASHSEED=0` расхождения те же (23 файла).

Причина — SQL: **56 из 59** запросов с `GROUP BY` в `src/compute/` не имеют
`ORDER BY`, и DuckDB возвращает группы в порядке параллельной агрегации.

| Файл | `GROUP BY` | с `ORDER BY` | без |
|---|---:|---:|---:|
| block0.py | 5 | 1 | 4 |
| block1.py | 20 | 0 | 20 |
| block2.py | 6 | 0 | 6 |
| block3.py | 4 | 0 | 4 |
| block4_seo.py | 23 | 1 | 22 |
| cost_summary.py | 1 | 1 | 0 |
| **итого** | **59** | **3** | **56** |

Значения при этом совпадают — меняется порядок строк. Опасно то, что
`evidence_id` присваивается **по позиции**: в одном прогоне `d08:0` — кампания
709054995, в другом — 119193036, а поле `related` ссылается именно на этот
позиционный ID (`['d08:0']`). То есть между прогонами меняется смысл
перекрёстных ссылок, и находка, утверждённая аналитиком по одному прогону, при
пересчёте указывает на другую сущность.
