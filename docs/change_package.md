# Пакет изменений: воронки, экономика и компактный LLM-анализ

Статус: согласованный план, код ещё не изменён.

Этот документ — общий контекст для отдельных задач Codex. Новый чат не должен
восстанавливать решения из предыдущей переписки: все обязательные решения,
границы и критерии собраны здесь.

## 1. Цель пакета

Использовать максимум уже выгруженных данных и передавать в LLM минимальный,
но самодостаточный пакет:

- детерминированный код сохраняет, связывает и считает данные;
- LLM не ищет числа в сырых таблицах и не определяет бизнес-логику;
- LLM получает только кандидаты, контекст для их проверки и ограничения;
- новый клиент настраивается только через `clients/<name>/config.yaml`;
- отсутствие источника приводит к явной деградации, а не к падению;
- каждое изменение внедряется и коммитится отдельной микрозадачей.

## 2. Что уже установлено на данных Pognali

Эти факты нужны для регрессионной проверки, но не должны быть захардкожены:

- CRM: одна строка — оплаченная бронь, не уникальный клиент;
- CRM содержит не только брони через форму: есть звонки и визиты на месте;
- со слов клиента более 90% клиентов приходят с сайта;
- 90% — параметр только Pognali, а не правило продукта;
- основная наблюдаемая веб-конверсия — отправка формы бронирования;
- расходы указаны конечными суммами с НДС;
- расходы Директа также считаются конечными суммами с НДС;
- НДС не добавляется и не вычитается повторно;
- бюджеты и ведение показываются отдельно, затем складываются в общий расход;
- повторные клиенты пока не определяются: без стабильного customer ID считаются
  показатели на бронь, а не на уникального клиента.

Из первого прогона также известны технические дефекты:

- `goalsID` может приходить как `[]`, `[123]`, `[123,456]`; текущий парсер
  не удаляет скобки и теряет часть целей;
- по сырому `goalsID` для Pognali обнаружено 3 002 визита с открытием формы,
  634 с отправкой, 620 с обоими событиями;
- текущий canonical содержит только 606 открытий и поэтому искажает воронку;
- `goal_achievements` пуст, потому что массивы ID/времени/serial имеют разные
  длины; это не должно мешать сохранять сам факт достижения цели;
- S06 содержит полезные GSC+Wordstat-строки, но целиком исключается из analyze
  из-за соседней строки `unavailable` по Вебмастеру;
- девять находок первого LLM-прогона отклонены из-за английских значений
  `status`, тогда как валидатор принимает русские;
- текущий `_analyze_input_pack.json` имеет размер около 512 КБ;
- C06 уже был рассчитан, но LLM не выбрал его в итоговые находки.

## 3. Неподвижные архитектурные правила

Сохраняются инварианты проекта:

1. Слои: `raw -> canonical -> metrics -> findings -> report`.
2. `extract`, `transform`, `compute` не используют LLM.
3. LLM разрешён только в `analyze` и не пересчитывает числа.
4. Parquet остаётся источником истины canonical-слоя.
5. Настройки клиента находятся в `clients/<name>/config.yaml`.
6. `report` не запускается без утверждённых находок.
7. Рабочие ID проверок — только D/A/T/C/S.
8. Деньги хранятся как `float`, проценты — долями.
9. Один активный чат Codex работает с репозиторием одновременно.
10. Каждая микрозадача меняет только свой `allowed_files` и завершается
    целевыми тестами и отдельным коммитом.

## 4. Принятые продуктовые решения

### 4.1. Все цели сохраняются до интерпретации

Canonical должен содержать отдельную таблицу `visit_goals.parquet`:

| Поле | Смысл |
|---|---|
| `visit_id` | ID визита Метрики |
| `goal_id` | ID достигнутой цели |
| `achievement_count` | число срабатываний цели в визите |

Одна строка — уникальная пара `visit_id x goal_id`. Таблица строится только по
`ym:s:goalsID` и не зависит от доступности `goalsDateTime` или serial number.
Временная таблица `goal_achievements`, если её можно построить строго, остаётся
отдельным более сильным источником.

### 4.2. Связи целей задаёт пользователь

LLM не предлагает и не утверждает связи целей. Клиентская конфигурация содержит
последовательность этапов. Несколько ID могут обозначать один этап.

Минимальный контракт:

```yaml
funnels:
  booking:
    - stage: form_open
      goal_ids: [371497083]
    - stage: form_submit
      goal_ids: [371497275]
```

Других обязательных полей нет:

- `required` не используется;
- индивидуальный `dedupe` не используется;
- этап достигнут, если в визите есть любая цель этапа;
- все показатели считаются по уникальным визитам;
- последний этап считается итоговой конверсией воронки;
- альтернативный путь описывается отдельной воронкой.

Для каждой воронки считаются:

- визиты на каждом этапе;
- переход между соседними этапами;
- переход от первого к последнему этапу;
- визиты предыдущего этапа без следующего;
- визиты позднего этапа без раннего;
- повторные срабатывания целей как QA, но не как дополнительные конверсии;
- разрезы по месяцу, каналу, устройству и входной странице.

Если времена событий доступны, порядок проверяется дополнительно. Если времени
нет, поздний этап без раннего называется аномалией трекинга или альтернативным
сценарием, а не невозможным поведением пользователя.

### 4.3. CRM-семантика настраивается

Поддерживаемые значения `crm_csv.record_unit`:

- `paid_booking` — оплаченная бронь;
- `lead` — обращение;
- `opportunity` — потенциальная сделка;
- `unknown` — семантика не подтверждена.

Пустое значение не должно молча превращаться в факт. Для Pognali явно задаётся
`paid_booking`. При `unknown` денежные показатели, требующие факта оплаты, не
считаются и получают объяснение деградации.

Для `paid_booking` считаются:

- количество броней;
- общая выручка;
- средняя выручка на бронь;
- медианная выручка на бронь;
- при наличии стабильного customer ID — отдельные показатели на клиента.

До появления customer ID нельзя называть показатель «доходом на клиента».

### 4.4. Расходы считаются в конечных суммах с НДС

Экономика использует фактически уплаченную конечную сумму:

- НДС не добавляется;
- НДС не вычитается;
- бюджет и ведение являются разными компонентами;
- компоненты складываются один раз;
- общий итог сопровождается детализацией по компонентам и каналам.

Универсальная конфигурация:

```yaml
spend_components:
  - id: direct_media
    channel: direct
    kind: media
    source: canonical_costs
    source_tag: direct

  - id: direct_management
    channel: direct
    kind: management
    source: monthly_fixed
    amount_rub_month: 28500
```

Поддерживаемые `source` первой версии:

- `canonical_costs` — сумма из canonical `costs` по `source_tag`;
- `monthly_fixed` — конечная ежемесячная сумма из config.

`id` компонента уникален. Один `source_tag` canonical-расходов нельзя подключить
двумя компонентами. Для каждого месяца выводятся компонент, канал, вид расхода
и сумма; затем — итоги канала и общий итог.

### 4.5. Экономика привлечения универсальна

В коде запрещены Pognali, доля 90% и конкретные ID целей. Клиент выбирает одну
или несколько моделей:

```yaml
acquisition_models:
  - id: estimated_site_booking
    mode: crm_share_estimate
    crm_share: 0.90
    spend_components:
      - direct_media
      - direct_management
      - seo_management
      - maps_media
      - maps_management

  - id: tracked_booking
    mode: tracked_funnel
    funnel: booking
    stage: form_submit
    spend_components:
      - direct_media
      - direct_management
```

Режимы:

- `crm_attributed`: CRM имеет надёжный источник, расход делится на оплаченные
  записи соответствующего канала;
- `crm_share_estimate`: число CRM-записей умножается на клиентскую долю;
- `tracked_funnel`: знаменатель — уникальные визиты указанного этапа воронки.

Каждый результат хранит:

- числитель и его компоненты;
- знаменатель и способ его получения;
- формулу;
- результат;
- единицу результата;
- допущения;
- ограничения;
- метку `actual`, `estimate` или `tracked_proxy`.

Названия результата зависят от знаменателя:

- «стоимость оплаченной брони»;
- «оценочная стоимость сайт-брони»;
- «стоимость отслеженной отправки формы»;
- не использовать `CAC`, если не известен уникальный новый клиент.

Для канального `tracked_funnel` модель может содержать фильтр по сохранённому
полю визита, например `source_group_resolved=ad`. Без надёжного фильтра
канальный результат не считается.

### 4.6. Сезонность — отдельная бизнес-метрика

S06 продолжает проверять, объясняет ли сезонность SEO-аномалию. Дополнительно
создаётся независимый компактный `seasonality.json`, который сопоставляет по
месяцам:

- индекс спроса Wordstat;
- визиты;
- итоговый этап выбранной воронки;
- CRM-записи;
- CRM-выручку.

Вывод содержит только месячные индексы, пики, провалы, доступные YoY-сравнения
и конфликты направлений. Сырые запросы Wordstat в LLM-пакет не передаются.

### 4.7. LLM не ищет кандидатов в сырых метриках

Каждая строка метрики получает единый аналитический контракт:

- `candidate: true|false`;
- `row_role: candidate|summary|baseline|context|limitation|detail`;
- `candidate_reason`: короткий стабильный код;
- `context_refs`: ссылки на необходимые baseline/context-строки.

Формулы проверок при этой разметке не меняются. После расчёта блоков
детерминированный сборщик создаёт `analysis_candidates.json`.

## 5. Контракт компактного LLM-пакета

`analyze` не должен загружать все `data/metrics/*.json`. В LLM уходят:

1. краткий контекст клиента и окно данных;
2. детерминированные кандидаты и только связанный с ними контекст;
3. компактные воронки;
4. компактная экономика;
5. компактная сезонность;
6. ограничения и confidence caps;
7. только заполненные качественные inputs;
8. coverage: сколько проверок рассчитано, кандидатов включено и исключено.

Для повторяющихся структур используется формат `columns + rows`:

```json
{
  "columns": ["check_id", "segment", "metric", "value", "confidence"],
  "rows": [
    ["C06", "device=desktop", "open_to_submit_rate", 0.4595, "MED"]
  ]
}
```

Требования к сериализации:

- UTF-8 без ASCII escaping;
- компактный JSON без отступов для передаваемого артефакта;
- повторяющиеся названия и схемы задаются один раз;
- не использовать неочевидные односимвольные ключи;
- не повторять полный `money_frame`, если те же данные есть в economics;
- не передавать строки `detail`, не связанные с кандидатом;
- `unavailable` фильтруется построчно, а не выбрасывает весь файл;
- один вызов LLM на прогон;
- детерминированный byte-cap с приоритетом: деньги, значимость, confidence,
  покрытие блоков;
- при достижении cap пакет содержит список и причины исключения кандидатов.

Цель для Pognali:

- менее 100 КБ вместо текущих примерно 512 КБ;
- C06 и S06 присутствуют;
- все детерминированные кандидаты помещаются без исключения;
- пакет не содержит полных сырых массивов метрик;
- размер и coverage записываются в аудиторский артефакт.

### 5.1. Контракт ответа LLM

- `status` задаётся enum русских значений непосредственно в JSON Schema;
- `confidence` и денежная категория также задаются enum;
- числовое evidence сверяется с источником;
- повторяющиеся сегменты одной проблемы объединяются в одну находку;
- лимит находок применяется после объединения;
- LLM формулирует вывод и действие, но не рассчитывает новые числа;
- LLM не повышает confidence и не скрывает ограничения.

## 7. Инструкция по запуску задач в отдельных чатах

### 7.1. Подготовка

1. Открыть локальный проект `D:\Projects\start-up\marketing-diagnostics`.
2. Убедиться, что предыдущая задача завершена и нет другой активной сессии.
3. Проверить `git status --short`; чужие изменения не сбрасывать.
4. Выбрать модель:
   - GPT-5.6 Sol, Medium — P01, P03, P05-P08, P10;
   - GPT-5.6 Sol, High — P02, P04, P09;
   - Max и Ultra не использовать.
5. Создать новый чат для одной задачи.

### 7.2. Универсальный промт запуска

Заменить `{TASK_ID}` на P01, P02 и так далее:

```text
Выполни только микрозадачу {TASK_ID} из docs/change_package.md.
Сначала прочитай AGENTS.md, затем общие разделы 1-5 документа и карточку {TASK_ID}.
Считай их полным контрактом задачи; предыдущего чата у тебя нет.
Читай только files_to_read и непосредственно импортируемые локальные модули.
Меняй только allowed_files. При конфликте первоисточников остановись и перечисли его.
Не делай попутных улучшений и не переходи к следующей задаче.
Сначала минимальная реализация, затем только указанные целевые тесты.
Проверь diff, обнови только строку {TASK_ID} в implementation_status и закоммить шаг.
Финал: изменённые файлы, результат, тесты, commit, blocker; максимум 12 строк.
```

### 7.3. После каждого чата

1. Прочитать финальный ответ и blocker.
2. Просмотреть diff и убедиться, что изменены только `allowed_files`.
3. Проверить результат целевых тестов.
4. Убедиться, что создан один логический commit.
5. Если задача остановилась на конфликте, не запускать следующую.
6. Если всё прошло, открыть новый чат и запустить следующий ID.

### 7.4. Что нельзя делать

- не вставлять все десять задач в один чат;
- не запускать задачи параллельно в одном worktree;
- не разрешать новой задаче исправлять соседние файлы;
- не запускать полный pytest без отдельного запроса;
- не запускать `analyze` с реальным LLM до приёмки P10;
- не принимать `CAC` или «доход на клиента», если считается бронь;
- не добавлять или вычитать НДС из конечных сумм;
- не разрешать LLM классифицировать связи целей;
- не скрывать omitted candidates или деградацию источника.

## 8. Финальный контроль после P10

До первого платного LLM-прогона вручную подтвердить:

- raw/canonical counts целей совпадают после нормализации формата;
- итоговая воронка Pognali показывает open, submit и gap;
- CRM называется набором оплаченных броней;
- средняя и медианная выручка считаются на бронь;
- 90% отображается как клиентское допущение Pognali;
- бюджеты и ведение видны отдельно и в общем gross-итоге;
- tracked proxy не называется точным канальным CAC;
- сезонность содержит Wordstat и доступные бизнес-ряды;
- C06 и S06 входят в LLM-пакет;
- все статусы ограничены русским enum;
- input pack меньше 100 КБ и содержит coverage;
- LLM будет вызван один раз.

следует объединять с P10: сначала принимается детерминированный пакет, затем
отдельно расходуются токены модели.
